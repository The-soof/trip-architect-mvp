# Database structure changes — backlog

Operational and structural database work for Trip Architect, surfaced largely by the
**2026-06-05 production OOM incident** (a Cartesian-product query in `recover_interrupted_trip_jobs`
exhausted memory at boot; fixed by switching to `selectinload`). These are *infrastructure/structure*
items — distinct from feature data work like the IATA airport-code dataset.

Current state for reference:
- **Prod (Railway):** PostgreSQL — persistent. ✅
- **Local/dev + tests:** SQLite (`sqlite:///./backend/trip_architect.db`).
- **Schema migrations:** hand-written `ensure_runtime_schema()` in `backend/app/db/bootstrap.py`
  (manual `ALTER TABLE … ADD COLUMN` checks) plus `Base.metadata.create_all()` at startup.

Rough priority: **#4 backups (now)** → **#3 data hygiene (soon)** → **#1 migrations** → **#2 local parity**.

---

## 1. Adopt a real migration tool (Alembic)

**What:** Replace the hand-rolled `ensure_runtime_schema()` + `create_all()` approach with
Alembic versioned migrations (autogenerated from SQLAlchemy model changes, tracked in a version table).

**Why it's important:**
- Today every new column/table is hand-coded as an idempotent `ALTER TABLE` check. That's easy to
  forget, has **no version history and no rollback**, and grows more fragile with each change.
- Multiple environments (local SQLite vs prod Postgres) can drift silently.
- Alembic gives reviewable, ordered, reversible migrations and a clear "what's been applied" record.

**When to do it:** Soon-ish — ideally **while the schema is still small enough to baseline cleanly**,
and definitely before schema changes get frequent or before there's irreplaceable user data. Not an
emergency.

**Reasons not to implement yet:**
- Adds per-change overhead (generate + review a migration for every model edit) and a learning curve.
- Introducing it mid-stream requires **carefully baselining the existing prod schema** (an initial
  "stamp") so Alembic doesn't try to recreate existing tables — a delicate one-time step.
- For a solo, pre-launch project with infrequent schema changes, the current approach is "good enough."

---

## 2. Postgres locally for dev/prod parity

**What:** Run PostgreSQL locally (Docker container, or a dedicated Railway dev database) for
development instead of SQLite.

**Why it's important:**
- SQLite and Postgres differ in types, concurrency, locking, JSON handling, case-sensitivity, and —
  critically — **performance characteristics**. The OOM/Cartesian bug was **invisible on SQLite**
  because the dev DB is tiny and SQLite tolerated the query.
- Parity catches Postgres-only bugs (locking, query-plan blowups, type quirks) *before* production.

**When to do it:** When DB bugs start costing real time (this incident is a signal), or before launch.
Low effort with Docker.

**Reasons not to implement yet:**
- SQLite is zero-setup and fast to iterate on; the deterministic test suite runs on it cleanly.
- For a solo MVP, the friction may not pay off until closer to launch.
- **Middle path:** keep SQLite for day-to-day dev but run the test suite (or a smoke check) against
  Postgres in CI to catch parity issues without changing the local loop.

---

## 3. Data hygiene / retention (prune `agent_runs`, clear stuck trips)

**What:** Add retention/pruning for high-churn tables — especially `agent_runs` (every regenerate
appends rows) — and a way to clear or time-out trips stuck in `planning` / `itinerary_planning` /
`selected`. Optionally cap or age-off `agent_runs` per trip.

**Why it's important:**
- This data **directly fueled the OOM**: many `agent_runs` + stuck trips were the multiplier in the
  Cartesian explosion, and stuck trips are re-examined by recovery on **every boot**.
- Unbounded growth slowly degrades query cost and clutters the workspace/observability views.

**When to do it:**
- **Now (one-off):** clear the currently-stuck trips so recovery stops re-processing them each boot.
- **Soon:** a retention policy before user/data volume grows. The `selectinload` fix bought breathing
  room, so it's no longer an emergency.

**Reasons not to implement yet:**
- Pruning needs care: the **latest itinerary run carries `travel_notices`**, and runs power the
  observability/next-steps UI — deleting the wrong ones breaks features. Retention rules must be
  designed around that.
- Pre-launch with little data, urgency is low now that the query no longer explodes.

---

## 4. Durability & ops (backups, connection limits, kill the SQLite footgun)

**What:**
- Confirm **Railway Postgres backups** are enabled.
- Guarantee `DATABASE_URL` in prod is always the Postgres reference — never the local SQLite value.
  Consider **failing fast (or refusing to boot) on SQLite when `APP_ENV=production`** so it can't
  silently run on ephemeral storage.
- Review connection-pool sizing vs Railway's Postgres connection limit.

**Why it's important:**
- **SQLite on Railway wipes all data on every redeploy** (the warning in the startup logs). A
  misconfigured `DATABASE_URL` would silently destroy all users/trips.
- Backups protect against bad migrations, accidental deletes, and corruption.
- Connection-limit awareness prevents pool exhaustion under real traffic.

**When to do it:**
- **Now:** enable backups (cheap insurance the moment there's any real data) and add the
  prod-SQLite guard.
- **Before launch:** pooling review.

**Reasons not to implement yet:**
- With zero real users there's nothing to back up or lose *yet*, so urgency is low.
- Tuning the connection pool before there's traffic is premature.
- The only genuine "do it now" items are enabling backups and preventing a prod SQLite fallback.
